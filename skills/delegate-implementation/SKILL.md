# 実装の委譲と統合

目的は、独立して進められる仕事を適切な実装者に渡し、要求を満たす成果物へ統合すること。
親エージェントは作業分割、境界の調整、レビュー、統合、完了判定を担当する。
直接実装も選択肢に含め、委譲のためだけの分割や手順を増やさない。
ユーザーが直接実装を指定した仕事は自分で行う。

## 1. 到達点と作業境界を決める

適用されるリポジトリ規約、既存の変更、要求と受け入れ条件を確認する。
ローカル修正、PR作成、mergeのどこまで求められているかを会話から判断する。
このスキルを使っただけでPR作成やmergeの依頼があったとは扱わない。
すでに与えられた許可は引き継ぐ。

仕事は、単独で説明・実装・検証できる成果物を単位に分ける。
Issue番号、ファイル数、エージェント数から機械的に分割しない。

- 独立した変更は並行して進める。
- 同じ契約や共有ファイルに依存する変更は、契約を先に確定するか順番に進める。
- 密接に絡む小さな変更は一人にまとめる。分割後の統合コストも考慮する。
- 調査やレビューだけの委譲には、編集用のbranchやworktreeを用意しない。

複数の仕事がある場合だけ、担当、依存先、編集範囲、作業場所、状態を短い表で管理する。
開始時に、分担、実行手段、作業場所を選んだ理由、到達点を簡潔に伝える。

## 2. 実行手段を選ぶ

ユーザーが実装者を指定した場合はその指定を優先する。
指定がなければ、利用可能な機能を確認して次の順で判断する。

| 手段 | 選ぶ場面 |
| --- | --- |
| 直接実装 | 小さい、分割しにくい、または委譲の待ち時間・引き継ぎコストが利益を上回る |
| ネイティブのサブエージェント | 独立した仕事があり、必要なツール、編集権限、連絡・継続機能を利用できる |
| 外部CLI | 指定された実装者が外部CLIである、またはネイティブ委譲では必要な実行環境・機能を得られない |

同じ製品への委譲では、利用可能なネイティブ機能を第一候補にする。
CodexからCodex、ClaudeからClaudeという理由だけで別CLIプロセスを起動しない。
製品名から機能を推測せず、このセッションで公開されたツールの説明を確認する。
サブエージェント機能がなければ、外部CLIまたは直接実装を選ぶ。

ネイティブ委譲では[references/native-agents.md](references/native-agents.md)を読む。
外部CLIでは[references/external-cli.md](references/external-cli.md)と、選んだ実装者の参照だけを読む。

- [Claude CLI](references/implementer-claude.md)
- [Codex CLI](references/implementer-codex.md)
- [Devin CLI](references/implementer-devin.md)

## 3. 作業場所を選ぶ

実行手段とファイルの隔離は別の判断である。
サブエージェントにも専用worktreeは使えるし、外部CLIにも既存の作業ツリーは使える。
実際に作業場所を指定できるか、共有・隔離の範囲はどこかを確認する。

| 作業場所 | 選ぶ条件 | 統合方法 |
| --- | --- | --- |
| 既存の作業ツリーを一人で使う | 単一の変更系列で、既存の変更を保護できる | その場で差分をレビュー |
| 作業ツリーを共有する | 編集範囲を分離でき、Git操作と共有資源を親が調整できる | 全担当の編集完了後に統合検証 |
| 専用worktree | 別branchで並行開発する、別案を試す、既存の変更と分離する必要がある | 差分またはコミットを取り込み、統合後に検証 |
| 別環境 | ローカルでは得られない実行環境やセキュリティ隔離が必要 | 成果物の回収方法を起動前に決める |

共有時はファイルまたはディレクトリ単位で書き込み担当を一意にする。
同じファイルの別行というだけでは並列編集を認めない。
lockfile、生成物、依存インストール、開発サーバー、DB、ポートも共有資源として調整する。
親も実装する場合は担当範囲を持ち、子の編集中の範囲を変更しない。
担当範囲を広げる必要が出たら、関係する編集を止めて再割り当てする。

共有作業ツリーでは、indexとbranchを変更するGit操作を親だけが行う。
子はcommit、stash、checkout、rebaseなどをせず、未コミットの変更を返す。
全体がcleanであることを子の完了条件にしない。既存のユーザー変更を消してcleanにしない。

専用worktreeは自動隔離機能が既に作成していればそれを利用し、重ねて作らない。
作成前に起点となるcommitとbranch、既存の未コミット変更を引き継ぐ必要の有無を確認する。
worktreeには既存作業ツリーの未コミット変更は自動で入らない。
Gitの管理情報は共有されるため、worktreeをセキュリティ境界として扱わない。
セッションを取り違えるCLIなら作業ディレクトリを分けるか逐次実行する。

## 4. 実装者へ渡す共通契約

ネイティブではツールの指示メッセージ、外部CLIではプロンプトまたは指示書で渡す。
次の情報が揃えばよく、別ファイルや決まった見出しは必須ではない。

- **目的と完了条件**: 変える外部挙動、受け入れ条件、対象外。
- **根拠**: 仕様、関連コード、再現手順、適用される規約への参照。必要な規約は明示して読ませる。
- **担当境界**: 編集範囲、作業場所、共有している相手、Git操作の担当。
- **検証**: 変更に必要なチェック、リポジトリ必須チェック、実行分担。
- **返却内容**: 変更点、変更ファイル、検証したコードの状態・コマンド・結果、未解決事項。

担当外の変更が必要、仕様が未確定、権限や環境が不足という場合は、根拠と必要な判断を返させる。
テスト期待値の変更や回避コードで問題を隠して完了にしない。

実装担当へ渡すのは原則として編集と検証の権限である。
push、PR・Issue操作、CI操作、merge、branch・worktree管理は親が担当する。
専用worktreeでのローカルコミットは回収に役立つ場合だけ子へ割り当てる。
コミットのためだけにsandboxや承認機構を無効にしない。

## 5. 進行を管理し、成果物を統合する

仕事とagent/session IDを対応づけ、修正依頼は原則として同じ担当へ返す。
継続できなければ、現在の差分、判断済み事項、検証結果、残作業を新担当へ渡す。
担当交代前に旧担当を停止し、遅れて返った結果を重ねて適用しない。

待機中は独立した親の仕事を進める。
並列度は編集の独立性と利用可能な資源で決め、空き枠を埋めるために仕事を作らない。
失敗時は原因に応じて指示、分割、環境を変える。同じ失敗を同じ条件で無期限に再試行しない。
外部判断が必要な箇所は保留し、進められる仕事を続ける。

レビューでは、実装者の説明と実際の差分を照合する。
仕様への適合、対象外変更、重要な境界条件、必要な文書更新を確認する。
修正依頼は不適合箇所、その根拠、修正後に観測できる条件を具体的に伝える。

検証結果には対象を対応づける。コミット済みならSHA、未コミットなら確認した差分と検証後の変更有無を記録する。
共有作業ツリーで他担当が編集中の結果は、その後の統合状態の合格証拠にはしない。

- 信頼できる実行結果があり、対象コードと環境が同じなら、親が同じチェックを機械的に繰り返す必要はない。
- 出力が確認できない、結果と対象が不一致、重要な懸念が残る場合は親が再実行する。
- 統合、競合解消、依存変更の後は、その影響を受けるチェックを実行する。
- リポジトリが要求する最終チェックは省略しない。CIは現在の対象SHAで確認する。

worktreeからの回収は、変更のまとまりに応じてmerge、cherry-pick、patchから選ぶ。
共有作業ツリーの変更は既に反映されているので、報告内容を再適用しない。
取り込み中は対象への書き込みを止め、既存変更を保護してから統合する。

## 6. 依頼された到達点まで完了させる

PR、CI、複数Issue、mergeが対象なら[references/github-workflow.md](references/github-workflow.md)を読む。
ローカル作業だけならGitHub運用の手順を追加しない。

作業場所やbranchに想定外の変更がないか確認する。
広い範囲のGit状態を比較する必要がある場合だけ、
[references/repository-audit.md](references/repository-audit.md)の補助スクリプトを使う。
事後比較を権限制限の代わりや、越境がなかったことの完全な証明にはしない。

このタスクで作ったworktreeや一時ファイルは、実行終了と成果物回収を確認してから清掃する。
dirty、未回収、未保存の成果物がある場所は削除せず、残したパスと理由を報告する。
既存または他タスクの資源は清掃対象にしない。
ローカル実装が到達点なら、保存済みのローカル成果物を完成として扱い、清掃のためにpushしない。

最後に、変更内容、検証結果、到達点、未解決事項を報告する。
PRがあればURLと状態、一時資源が残ればパスと理由を添える。
実装済み、検証済み、PR作成済み、CI成功、mergedを区別する。

## 実装担当としてこのスキルを読んだ場合

親から渡された担当範囲と完了条件に従い、実装・検証・報告を行う。
このスキルを理由に全体の計画やGitHub運用を引き取らない。
再委譲は親が認めた場合だけ行う。
